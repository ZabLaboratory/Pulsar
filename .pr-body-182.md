## Summary

Implements ADR-005 §3.4 (issue #182): `pulsar:OutputFailed`, a structured
vendor event carrying the closed 7-class `reason_class` set, replacing the
`errOut`/`blog(LOG_WARNING)` dead end that left every output failure
invisible to consumers except by scraping stdout.

- `hookOutputSignals` (`pulsar-frontend-stub.cpp`) now extracts `code` and
  `last_error` from the `"stop"` signal `calldata_t*` it previously ignored,
  for both the legacy stream output and virtualcam.
- `DestinationRegistry::start` / `start_all` (`plugin-main.cpp`) route a
  synchronous `obs_output_start` refusal through the same event.
- Classification is centralized in one new header-only target,
  `plugins/pulsar-output-classify` (mirroring the existing
  `pulsar-nv-secure-load` pattern), so the two binaries that need it
  (`pulsar-frontend-stub`, a static lib with no obs-websocket vendor of its
  own, and `pulsar-multi-stream`, the DLL owning the `"pulsar"` vendor) can
  never classify the same `(code, last_error)` differently — the R4 risk the
  ADR calls out explicitly (a drifted class is worse than none).
- `pulsar-frontend-stub` reaches `pulsar-multi-stream`'s vendor through
  libobs's own global proc handler — the same mechanism
  `obs-websocket-api.h` itself uses to find obs-websocket — registered in
  `obs_module_post_load`, after `g_vendor` exists.
- `docs/PROTOCOL.md`: `OutputFailed` event entry, the closed `reason_class`
  table, and the RC5 correspondence table against
  `Prism/src/main/broadcast-url.ts`'s `PERSISTENT_RTMP_SIGNATURES` /
  `TRANSIENT_RTMP_SIGNATURES`.

## RC5 — no orphan signature

Every signature Prism scans for maps to exactly one `reason_class` (table in
`docs/PROTOCOL.md` §"Correspondence table — RC5"):

- `PERSISTENT_RTMP_SIGNATURES` (`unauthor`, `invalid (stream )?key`,
  `authenticat`, `403`) → `auth_rejected`.
- `TRANSIENT_RTMP_SIGNATURES` (the three `-3` patterns) →
  `ingest_dropped`, on the reading that `OBS_OUTPUT_INVALID_STREAM` (the code
  behind libobs's `-3`) means the RTMP connection was established and the
  server then refused the stream before diffusion started — flagged as a
  judgment call, not a certainty, in both the header comment and the
  PROTOCOL.md table.

`ingest_unreachable`, `encoder_failed`, `config_rejected`,
`disconnected_local`, `unknown` have no Prism signature — Prism doesn't
scrape stdout for those cases today. Not an RC5 orphan (every *Prism*
signature has a class); it means those classes were previously invisible to
Prism's own scraping.

## Écarts / hypothèses posées

- **`code -3` → `ingest_dropped` vs `ingest_unreachable`**: genuine judgment
  call, not a certainty — see the header comment and PROTOCOL.md. Flagging
  for review rather than silently deciding.
- **`disconnected_local` trigger**: no libobs code path cleanly maps to
  "locally provoked, not a config/auth/ingest/encoder issue" from
  `(code, last_error)` alone. Implemented as: any non-success code on a
  **local** output (virtualcam — no ingest/auth surface at all) is
  unambiguously local. Network-capable outputs never resolve to this class
  in the current implementation; flagging as a scope note rather than a
  silent gap, since the ADR's own description ("Arrêt provoqué localement
  hors demande du client") doesn't specify a concrete trigger to test against
  for the streaming/destination case.
- **`OBS_OUTPUT_NO_SPACE` (-7)**: falls to `unknown` — no class in the closed
  7-set fits "disk full" (relevant to `vod_local` destinations). Consistent
  with the ADR's own design (`unknown` is legitimate), not a bug.
- **`phase` values (`"start"` / `"active"`)**: not literally enumerated in
  ADR-005 §3.4 (only `output`/`code`/`last_error`/`reason_class`/`session`
  are named); chosen to distinguish a synchronous start refusal from an
  abnormal stop while active. Documented in PROTOCOL.md.
- **`session` field**: left empty per the issue's owned scope (wired by a
  later work unit, ADR §3.3's correlation key).
- No live build/runtime verification of the cross-plugin proc-handler bridge
  (frontend-stub → multi-stream's vendor) was possible in this environment —
  it's a straightforward, existing-pattern use of `proc_handler_add` /
  `proc_handler_call` (mirrors what `pulsar-multi-stream`'s own
  `output_id_for_kind`/etc already use internally, and what
  `obs-websocket-api.h` itself does to reach obs-websocket), but CI's
  `offline-probes` job is the first real exercise of it.

## Scope

Excluded per the issue: aggregate verdict (issue D), no change to v5 base
events, no retry policy, nothing on the Prism side, no ongoing maintenance
of the correspondence table (RC5 note in PROTOCOL.md says so explicitly).
