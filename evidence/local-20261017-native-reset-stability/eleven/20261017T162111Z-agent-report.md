## Two waiters and the contended lock

In dump TID 18964 (`libobs: graphics thread`) has a reliably walked stack ending at `NtWaitForSingleObject` → `WaitForSingleObjectEx+0xaf` → `pthread_mutex_lock+0x12f`. Its caller is the plugin frame `capture-effects.cpp:439`, `obs_get_source_by_name(f->parent.c_str())`. TID 8784 (`Thread (pooled)`) independently has the same wait stack and lock argument; its caller is `obs-websocket` `Request::AcquireSource+0x3b1`, `Request.cpp:251`, which also calls `obs_get_source_by_name`.

The saved-register slots in the exact KERNELBASE frame yield the same pthread argument pointer for both waiters: `&main_canvas->sources_mutex` at `0x21422523558`. `pthread_mutex_lock` dereferences that pointer to the internal mutex object at `0x2142252dd50`; the exact KERNELBASE prologue saves the caller's RBX, which was the internal mutex object pointer. Both threads therefore wait on the same internal mutex object and the same event handle. The stack walker’s AddrReturn field at `0x2142252dd50` was a misleading interpretation of this saved RBX value; it is not an instruction address.

The exact obs PDB maps `obs.dll+0x7c822` to inline frame `get_context_by_name+0x32`, `obs.c:2083`. The `obs_get_source_by_name` disassembly performs the ordinary global-source lookup first; if it returns null, it tail-calls the same helper against `main_canvas->sources` and passes the mutex field at `main_canvas+0x178`. The raw slot reader records the pthread caller stack pointer `p`, its immediate return slot at `p+0x78` (`obs.dll+0x7c822` in both threads), and the enclosing helper return slot at `p+0xb8`: `pulsar-capture-effects.dll+0xff26` for graphics and `obs-websocket.dll+0x13edb1` for the worker. The exact PDB/source mappings in the caller-symbol record map those to `capture-effects.cpp:439` and `Request.cpp:251`. The helper returns directly to these external callers, matching the wrapper tail-call fallback. This localizes the contended lock to the main-canvas source-name lookup fallback. It does not identify who currently owns the mutex.

The per-thread raw stackwalk records are `20261017T162111Z-stackwalk-155459-18964.txt` and `20261017T162111Z-stackwalk-155459-8784.txt`. ## What remains unknown

The dump has no HandleDataStream and omits memory at `0x21422523558` and `0x2142252dd50`. The current evidence proves two waiters and identifies their common mutex and call paths; it does not prove the holder thread, a recursive call, a lock cycle, or a product defect’s exact initiating instruction. A later freeze collection should capture those two small heap ranges and relevant owner/thread state, plus HandleDataStream if available, while retaining the existing 64 MiB bound. Do not infer owner from the wait event handle or current stacks alone.
